# Design: Phase 2.1 角色主标记与审批路由收敛

## Problem Statement

项目里同一个考核人角色出现 2 个人时，系统现在把审批/打分任务**同时发给两个人**。业务要的是：同一角色若出现 2 人，标一个「主」，只有主审批/打分。当前 `is_primary_pd` 字段语义是「项目级唯一负责人」，粒度错；任务生成是「角色级全员 fan-out」，也错。两处都要对齐到「每 (项目, 阶段, 角色) 一个主」。

## Demand Evidence

- 会话中用户原话：「一个项目如果出现了 2 个相同的考核人角色，但是人不一样，这个时候要标注一下，只需要其中一个审批就可以了。现在实际情况是，2 个人都可以收到审批。」
- 角色模型纠偏：「主 PD 实际上并不是主项目经理，应该是项目总监。」PD 标主的意义是「出现在项目里是为了让他能看见他当前管的有哪些项目、哪些人」。

## Status Quo（代码证据）

| 位置 | 现状 |
|---|---|
| `project_role_assignment.is_primary_pd`（V1__init.sql:89） | 布尔，注释「是否PD负责人」，**项目级唯一**（一个项目一个 true） |
| `RoleAssignmentService.markPrimaryPd`（130-151 行） | unmark 只按 `projectCode`，跨阶段跨角色会误删 |
| `ParticipationService.approve`（230-235 行） | 非 ADMIN「被分配到该项目即可」审批，不查角色、不查主 |
| `ParticipationService.notifyPrimaryPds`（324-359 行） | 通知 `is_primary_pd=true` 的人 |
| `TaskGeneratorService.generateTasksForEmployee`（175-180 行，launch 路径） | 循环同角色**所有人**，每人 `insertIgnore` 一条 PROJECT 任务 |
| `TaskGeneratorService.onParticipationApproved`（244-248 行，增量路径） | 同上，同样的全员 fan-out |

根因：`is_primary_pd` 是「项目级单主」，而任务生成是「角色级全员 fan-out」，两者都不对齐业务要的「每角色一主」。**两条路径都活**：launch = 周期发起时预生成；onParticipationApproved = 发起后新增参与人时增量生成。

## Target User & Narrowest Wedge

- ADMIN/PM：在角色分配里给「同角色第 2 人」标主。
- 各考核人角色：只有被标为主的那一个收到打分任务。
- PD（项目总监）：标主后看到自己管的项目与人（复用 Phase 2.1 校准的 PD 可见性）。
- 最小可交付：字段泛化 + 任务生成只发主 + 未标主时记差异报告。

## Constraints

- 不做角色枚举：任何角色出现 2 人都可标主，唯一性 =「每 (项目, 阶段, 角色) 一个主」。
- 参与录入审批该由谁批（是否走「主 PM」）**不在本次范围**，后面再说。
- 打分任务只发给被标为主的那一个；同角色 ≥2 人且无人标主 → 跳过该角色 + 记 `discrepancy_log` + **主动站内通知 admin 使用者**，不退回「都发」。

## Premises（已锁决策）

- **P1 字段泛化**：`is_primary_pd` → `is_primary`，语义从「项目级唯一负责人」改为「该角色在该项目阶段的唯一主审批人」。不新建第二列，避免 PD 叠两套概念。
- **P2 唯一性**：改为每 (project_code, project_stage, project_role_code) 至多一个 `is_primary=true`，DB 层用部分唯一索引兜底。
- **P3 任务生成收敛**：**两条路径都收敛**（launch 的 `generateTasksForEmployee` 175-180 行 + 增量的 `onParticipationApproved` 244-248 行），抽一个共享 helper `resolvePrimaryAssessors(assignedPersons)`：同角色多人时只给 `is_primary=true` 的人发任务；无主则跳过该角色 + 记差异 + 通知 admin。
- **P4 PD 可见性**：PD 可见范围 = `is_primary=true AND role=PD`，与 Phase 2.1 「PD 仅见标记为主 PD 的项目」同一句。
- **P5 参与审批路由推迟**：`approve` 的「谁批参与」与 `notifyPrimaryPds` 的语义保持现状，标 follow-up，不在本次改。

## 数据模型与状态机（本次增量）

- **迁移 V20**：
  1. `ALTER TABLE project_role_assignment RENAME COLUMN is_primary_pd TO is_primary;`（改列名 + 更新注释为「该角色在该项目阶段的唯一主审批人」）。
  2. 新增部分唯一索引：`CREATE UNIQUE INDEX uk_primary_per_role ON project_role_assignment(project_code, project_stage, project_role_code) WHERE is_primary AND deleted = 0;`（单人不标主时 `is_primary=false` 不进索引，不拦「1 人无需标主」）。
- **`RoleAssignmentService.markPrimaryPd` → `markPrimary`**：unmark 范围从只按 `projectCode` 改为按 `projectCode + projectStage + projectRoleCode`，再标当前分配；`assignEmployee` 里 `setIsPrimaryPd(false)` 改为 `setIsPrimary(false)`。
- **共享 helper `resolvePrimaryAssessors`**：抽一个私有方法 `List<ProjectRoleAssignment> resolvePrimaryAssessors(List<ProjectRoleAssignment> assignedPersons)`，返回「该角色该阶段该项目的标主集合」。两个调用点（launch 的 `generateTasksForEmployee` 175-180 行 + 增量的 `onParticipationApproved` 244-248 行）都改为：先 `resolvePrimaryAssessors`，恰好一个则只发该人；`assignedPersons.size()>1 && 无主` 时跳过该角色并记一条 `discrepancy_log(type='NO_PRIMARY_ASSESSOR', detail='角色 X 有 N 人未标主，任务未生成')`。`type` 枚举在 V14 的 `NO_POSITION_CONFIG/NO_ASSESSOR/NO_LEADER` 基础上新增 `NO_PRIMARY_ASSESSOR`。这样两处同源，不再各写一份过滤逻辑（DRY，见 Code Quality）。
- **主动通知 admin**：同一事务内，除记差异外，查 `user_role` 表 `role_type='ADMIN'` 的全部 `user_id`，经 `NotificationService.notifyBatch` 给每个 admin 发一条 `Notification`（`recipientId=userId`，`type='NO_PRIMARY_ASSESSOR'`，`targetUrl` 指向角色分配页，title/content 指明「项目 X 阶段 Y 角色 Z 有 N 人未标主，考核任务未生成」）。复用现有 `notifyPrimaryPds` 里「查 user_id → 组 Notification → notifyBatch」的同一套路。
- **`notifyPrimaryPds`**：本次不改逻辑，仅把查询列 `isPrimaryPd` 改为 `isPrimary`（字段改名后的编译级同步）；语义漂移（由「项目级 owner」变「所有角色主」）记为 follow-up，随「主 PM 谁批参与」一起定。

## Approaches Considered

- **A 通用 `is_primary`（采用）**：改列名 + 语义升级为「每角色一主」，一个字段覆盖所有角色。干净，不叠概念。
- **B 保留 `is_primary_pd` + 另加通用列（否）**：PD 会同时挂「项目级 owner」和「角色主」两套语义，后面必乱。
- **C 枚举角色白名单（否）**：用户明确否掉——「不管是什么角色，出现两个都可以标记」，不预判哪些角色撞车。

## Recommended Approach

A。字段泛化 + 部分唯一索引 + 任务生成收敛 + 未标主记差异，四步一次收敛；参与审批路由与通知语义推迟，避免在本次把「谁批参与」和「谁打分」两个不同审批混在一个改动里。

## Open Questions / Deferred

- 参与录入审批该由谁批（是否走「主 PM」）——用户明确「后面再说」。
- `notifyPrimaryPds` 的通知语义（项目级 owner vs 所有角色主）——随上一条一起定。
- `NO_PRIMARY_ASSESSOR` 差异的 `resolved` 闭环：HR 补标主后，已跳过的任务需手动重触发生成（复用参与记录重新审批 or 周期重新 launch），本次只记差异不自动补发。

## Success Criteria

- 同一角色 2 人在项目里时，只有标主的那一个收到打分任务，另一个不收到。
- 同角色 2 人无人标主时，差异报告里出现一条 `NO_PRIMARY_ASSESSOR`，且**不**出现「两人都收到」的误发任务；同时 admin 使用者在站内收到一条「未标主」通知。
- PD 标主后能在校准矩阵里看到 `is_primary=true AND role=PD` 的项目与人。

## The Assignment

开工前（实施解冻后）找 ADMIN/PM 确认一件事：同角色第 2 人被分配到项目时，UI 是「分配时就强制标主」还是「分配后提示、可稍后标主」（前者更顺，后者更灵活）。这决定前端交互，后端唯一索引与差异报告两种都兼容。

## Test Plan（实施解冻后补，先列项）

`resolvePrimaryAssessors` 单元测试（`TaskGeneratorServiceTest`，四象限）：

1. **1 人**：返回该人，正常发任务（不触发 NO_PRIMARY_ASSESSOR）。
2. **2 人恰好 1 个标主**：只返回标主者，未标主者不收任务。
3. **2 人无主**：返回空 → 跳过该角色 + 记 `NO_PRIMARY_ASSESSOR` 差异 + 通知 admin（verify notifyBatch 入参含 admin user_id）。
4. **2 人都标主**（DB 部分唯一索引应已拦截，但若绕过/历史脏数据）：防御性只发一个 + WARN 差异，不重复发两条。

其余回归：

- **`markPrimary` unmark 范围**：同项目不同阶段各有一主时，标新主不误删另一阶段的主（改前只按 projectCode，跨阶段误删）。
- **`ProjectService` 建项目回归**：PM 建项目后仍写 `isPrimary=true`（字段改名不丢语义），`ProjectServiceTest.java:271` 同步。
- **迁移 V20 幂等**：RENAME COLUMN + 部分唯一索引在「现存数据最多一个 is_primary_pd=true 每项目」前提下无冲突；验证无孤儿主（同角色同阶段双 true 会被索引拒绝，若现存脏数据则先清洗）。
- **集成**：同角色 2 人无主时走一遍 `launch` 与 `onParticipationApproved` 两条路径，各自只产出一条 `NO_PRIMARY_ASSESSOR` 差异 + 一条 admin 通知，且**不**出现「两人都收到」的任务。
