## Problem Statement

Phase 2.0、2.1 已交付且满意。Phase 2.2 补两个关键缺口：

1. **总裁确认是孤儿流程。** 现状：`PeriodController.confirm`（`/api/v1/periods/{id}/confirm`）`@PreAuthorize("hasRole('ADMIN')")`，`PeriodService.confirmPeriod` 一条 `CALIBRATING→CONFIRMED` 原子翻转就完事；`user_role` 里的「总裁」（`RoleType.PRESIDENT` → `ROLE_总裁`）没有任何 `@PreAuthorize`/数据隔离分支认它；`NEED_PRESIDENT_CONFIRM` 系统参数 V15/V21 种成了 'true' 但代码零引用（死开关）。需求澄清后的事实：总裁不止一个，不同项目由不同总裁负责最后确认；总裁本人登录点确认；可单项目退回（不影响其它项目流转）；全部确认后由 ADMIN 发布结果。
2. **用户管理靠 admin 手动建账号+密码。** 现状：`UserService.createUser(employeeId, username, password)` 要 admin 手敲用户名和密码。目标：admin 一键激活（账号=工号、初始密码=123456），所有人首登强制改密。

## 决策记录（本 session 已锁定）

- **D1 总裁挂接 + 登录身份**：负责总裁 = 项目角色分配（`project_role_assignment`）加「总裁」项目角色（标主，定位人）+ 用户管理（`user_role`）的「总裁」角色（功能权限）。两者都配。负责总裁按 **project_code** 一人（跨阶段同一人）。
- **D2 激活**：账号 = 员工工号（`username = employeeId`），初始密码 = `123456`（全局固定，系统参数可改）。
- **D3 强制改密**：后端硬门。`sys_user` 加 `must_change_password`；标记为 true 的用户登录后，除「改密」「登出」「me」外所有接口 403。所有人首登强制。
- **D4 发布状态机**：新增「项目确认」表追踪每个 (周期, 项目) 的确认进度；全部项目通过 → 周期 `CONFIRMED`（待发布，结果不可见）；ADMIN 发布 → 结果才对员工可见；退回单项目、走退回次数上限。

## Constraints

- Spring Boot 3.2.5 + PostgreSQL 16 + MyBatis-Plus + Flyway（当前最新 V25）。
- 两套角色体系：`user_role`（登录角色 → `ROLE_<type>`）vs `project_role`（项目内角色，roleCode/roleName，动态可配）。`project_role_assignment` 键为 (projectCode, projectStage, roleCode)，`is_primary` 部分唯一索引 `uk_primary_per_role`。
- 会话认证 + CSRF cookie；细粒度权限在各 Controller 的 `@PreAuthorize`。
- 周期状态机 `INIT/ONGOING/CALIBRATING/CONFIRMED/COMPLETED`；`assessment_period.status` 是 `VARCHAR(16)` 无 CHECK（新增状态无需迁移）。
- `isResultVisible(periodId)` 当前对 CONFIRMED/COMPLETED 返回 true（`ResultController.java:37` 依赖）。

## Premises

1. 总裁确认是真实业务动作（总裁本人登录、本人点确认），不是 ADMIN 代办的仪式。— 同意
2. 负责总裁按 project_code 一人，跨阶段同一人。— 同意
3. 结果发布是周期级全局动作，由 ADMIN 在「全部项目确认完成」后触发，且发布前员工看不到结果。— 同意

## Approaches Considered

### Approach A: 复用项目角色分配 + 总裁 user_role（采用）

负责总裁 = `project_role_assignment` 加 roleCode=`PRESIDENT` 的项目角色（`is_primary=true`），反查逻辑照抄 `PeriodMonitorService.resolvePrimaryPdByProject`（该函数用 `projectRoleCode='PD' AND is_primary=true`）。总裁登录用既有孤儿角色 `ROLE_总裁`，`@PreAuthorize("hasRole('总裁')")` + 按「我负责的项目」数据隔离。

### Approach B: project 表加专用字段 `president_employee_id`（否决）

否决原因：用户明确要求走「项目角色分配」（"需要在项目里添加总裁定位人员"）；专用字段放弃 `is_primary`、乐观锁、既有分配 UI 的复用，还引入第二套「谁是负责人」的真相源。

### Approach C: 最小版——周期级 CONFIRMED 一次翻转，只把「确认」按钮按项目拆给各总裁（否决）

否决原因：不满足「全部确认后 ADMIN 再发布」的明确需求，结果可见性无法与「确认完成」解耦（现状 CONFIRMED 即结果可见）。

## Recommended Approach

### 1. 周期状态机（第 6 态 PUBLISHED）

```
INIT → ONGOING → CALIBRATING ──全部项目确认完成──> CONFIRMED(待发布) ──ADMIN发布──> PUBLISHED(结果可见) ──ADMIN关闭──> COMPLETED(归档)
                     │
                     └─ project_confirmation 逐项目: PENDING ─确认─> APPROVED
                                                         └退回─> RETURNED ─(PD重校准重提交)─> PENDING
```

- **确认**从「周期级一次翻转」改为「逐项目确认」。`PeriodService.confirmPeriod`（CALIBRATING→CONFIRMED）废弃/重写：改为「每个项目 APPROVED 后，原子检查本周期是否已无 PENDING/RETURNED 项目，若无则 `CALIBRATING→CONFIRMED`」。
- **发布**新增 `publishPeriod`：`CONFIRMED→PUBLISHED`。**关闭**改为 `PUBLISHED→COMPLETED`（原来 `CONFIRMED→COMPLETED`）。
- **`isResultVisible`** 改为对 `PUBLISHED/COMPLETED` 返回 true（`CONFIRMED` 不再可见）。
- **状态涟漪（必须一并改）**：新增 PUBLISHED 后，所有按状态白名单的地方都要纳入 PUBLISHED——
  - `PeriodService.assertParticipatable` / `ParticipationService`（line 215/328/376 等）目前显式列 `CALIBRATING/CONFIRMED/COMPLETED` 拒绝参与写操作，PUBLISHED 会被漏过。建议反转为「仅 INIT/ONGOING 放行，其余一律拒绝」。
  - `PeriodMonitorService`（line 139/156）当前审批节点映射按 CONFIRMED/COMPLETED 判断，需补 PUBLISHED（展示「已发布」）与 CALIBRATING 的「总裁确认中」。
  - `PeriodController.confirm` 端点与 `PeriodService.confirmPeriod` 的前端调用点。

### 2. 数据模型（Flyway 迁移，V26/V27）

**V26 — 总裁项目角色 + 默认密码参数 + 强制改密列：**
```sql
-- 总裁项目角色（roleCode 固定为 PRESIDENT，解析器硬编码它）
INSERT INTO project_role (role_code, role_name, description, is_active)
VALUES ('PRESIDENT', '总裁', '项目负责总裁（最后确认人）', true)
ON CONFLICT (role_code) DO NOTHING;

-- 默认初始密码（激活账号用；可被系统参数页改）
INSERT INTO system_param (param_key, param_value, description)
VALUES ('DEFAULT_INITIAL_PASSWORD', '123456', '激活账号的默认初始密码')
ON CONFLICT (param_key) DO NOTHING;

-- 总裁退回次数上限（安全阀；与 MAX_RETURN_TIMES 语义不同，后者是 PD→评估人任务退回）
INSERT INTO system_param (param_key, param_value, description)
VALUES ('PRESIDENT_RETURN_TIMES', '3', '总裁单项目退回次数上限')
ON CONFLICT (param_key) DO NOTHING;

-- 强制改密标记
ALTER TABLE sys_user ADD COLUMN IF NOT EXISTS must_change_password BOOLEAN NOT NULL DEFAULT false;
COMMENT ON COLUMN sys_user.must_change_password IS '首登强制改密标记（true=登录后除改密/登出外一律403）';
```
注意 V15 的教训：`ON CONFLICT DO NOTHING` 不会覆盖已存在行。`DEFAULT_INITIAL_PASSWORD` 若此前未种过则无碍；若担心 UI 已建了同 code 的总裁角色，`ON CONFLICT DO NOTHING` 是安全的（不覆盖）。若需要强制固定 roleCode，用 `UPDATE`（同 V21 手法）。

**V27 — 项目确认表：**
```sql
CREATE TABLE project_confirmation (
    id                       BIGSERIAL PRIMARY KEY,
    period_id                VARCHAR(64) NOT NULL,
    project_code             VARCHAR(64) NOT NULL,
    status                   VARCHAR(16) NOT NULL DEFAULT 'PENDING',  -- PENDING/APPROVED/RETURNED
    return_count             INT         NOT NULL DEFAULT 0,
    return_reason            VARCHAR(500),
    confirmed_by_employee_id VARCHAR(64),
    confirmed_at             TIMESTAMP,
    deleted                  INT         NOT NULL DEFAULT 0,
    created_at               TIMESTAMP,
    updated_at               TIMESTAMP,
    version                  BIGINT      NOT NULL DEFAULT 0,
    CONSTRAINT uk_project_confirmation UNIQUE (period_id, project_code)
);
```
- 确认单元 = (period_id, project_code)，与「不管项目在哪个阶段」对齐（一个项目跨阶段一个确认项）。
- `return_count` + `PRESIDENT_RETURN_TIMES` 做退回次数上限；`confirmed_by_employee_id` 记确认人。
- 行在 `enterCalibration` 时生成：从本周期结果/任务表取 distinct project_code，逐个插 PENDING。

### 3. 负责总裁解析 + 数据隔离

- 新增 `PresidentService.resolvePrimaryPresident(projectCode)`：查 `project_role_assignment WHERE project_role_code='PRESIDENT' AND project_code=? AND is_primary=true AND deleted=0`，取 `employeeId`。跨阶段应同一人（admin 责任），若不一致视为配置异常，进差异报告提示。
- 总裁视角数据隔离：确认清单 = 「当前登录人 employeeId 是主总裁的项目」∩「本周期 project_confirmation 待确认项」。总裁看不到也操作不了别人的项目。

### 4. 后端端点 + 权限

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /api/v1/president/confirmations?periodId=` | `hasRole('总裁')` | 当前总裁负责的项目确认清单（数据隔离） |
| `POST /api/v1/president/confirmations/{id}/approve` | `hasRole('总裁')` | 单项目确认通过；全部通过后原子翻转周期 CONFIRMED |
| `POST /api/v1/president/confirmations/{id}/return` | `hasRole('总裁')` | 单项目退回（附 reason；return_count 达上限则拒） |
| `POST /api/v1/president/confirmations/{id}/resubmit` | `hasRole('PD')` | PD 重校准后重提交，RETURNED→PENDING |
| `PUT /api/v1/periods/{periodId}/publish` | `hasRole('ADMIN')` | CONFIRMED→PUBLISHED（发布结果） |
| `POST /api/v1/users/activate` | `hasRole('ADMIN')` | 一键激活：username=工号、password=DEFAULT_INITIAL_PASSWORD、must_change_password=true、授权角色 |
| `POST /api/v1/auth/change-password` | 登录即可 | 校验旧密码、bcrypt(12) 新密码、清 must_change_password |

- `PeriodController.confirm` / `PeriodService.confirmPeriod`：废弃，逻辑并入 approve 的「全部通过即 CONFIRMED」。
- `UserDetailsServiceImpl` 已把 `user_role` 映射成 `ROLE_<roleType>`，`RoleType.PRESIDENT` → `ROLE_总裁` 无需改；只需在 `@PreAuthorize` 与菜单里接入 `总裁`。
- `PeriodMonitorService.getPrimaryRole()` 角色列表 `{"ADMIN","PM","PD","评估人","员工"}` 需加 `总裁`（让总裁进监控看板）。

### 5. 强制改密硬门

- `login`（`AuthController`）与 `me` 返回体加 `mustChangePassword` 字段，前端据此跳改密页。
- 新增 `MustChangePasswordFilter extends OncePerRequestFilter`，注册进 `SecurityConfig` 过滤链：已认证且 `must_change_password=true` 时，除白名单 `/api/v1/auth/change-password`、`/api/v1/auth/logout`、`/api/v1/auth/me`、静态资源外，一律 403（返回 JSON `{"code":403,"message":"首次登录须先修改密码"}`）。后端硬门，前端跳转只是配合。
- `POST /api/v1/auth/change-password`：`{oldPassword, newPassword}`；`newPassword` 复用现有密码强度校验（如无则补长度/复杂度校验）；成功后 `must_change_password=false`。

### 6. 前端

- `LoginPage.jsx`：登录返回 `mustChangePassword=true` → `navigate('/change-password')`（强制）。
- 新页 `ChangePasswordPage`：改密成功 → 清标记 → `/dashboard`。
- `UserRolePage.jsx`：`新增用户` 3 字段 modal（line 245-274）改为「激活账号」——选员工 + 选角色（含「总裁」），后端自动工号/123456/强制改密。
- `AppLayout.jsx`：菜单加「总裁确认」入口（`ROLE_总裁` 可见）；`STAFF_ROLES`/`ALL_STAFF_ROLES` 按需含 `ROLE_总裁`。
- 新页 `PresidentConfirmPage`：列出「我负责的项目」确认项，逐项目【确认通过 / 退回（填原因）】。
- `PeriodConfigPage`（考核周期）：ADMIN 加「发布」按钮（CONFIRMED 时可用）。
- 项目角色分配页：对 `PRESIDENT` 角色提供「跨阶段一键同步」便捷操作，减少 admin 逐阶段重复分配。
- 监控看板：补 PUBLISHED 展示 + CALIBRATING「总裁确认中」。

## 影响面（改一处状态的涟漪，务必全覆盖）

新增 PUBLISHED 态 + 改 `isResultVisible` 语义，会影响所有「状态等值判断」点：`PeriodService`（`assertParticipatable`/`isResultVisible`/`closePeriod`）、`ParticipationService`（参与冻结三处）、`PeriodMonitorService`（审批节点映射）、`ResultController`（结果可见门）、`PeriodController`（confirm/close 注释与端点）。建议实现时把「哪些状态放行」收敛成一处常量/工具方法，避免再漏。

## Resolved in Review

- 发布/关闭分**两段**：保留 `PUBLISHED`（发布结果）+ `COMPLETED`（归档）。
- 退回后 PD 重校准**按项目**：校准 UI 补按项目过滤；PD 对退回项目重校准后走 `resubmit` 端点（`RETURNED→PENDING`）。
- 退回次数**保留上限**：`PRESIDENT_RETURN_TIMES`（默认 3）安全阀。
- 未分配总裁的项目：进差异报告提示「项目缺负责总裁」（新增差异类型，与 `NO_PRIMARY_ASSESSOR` 同类），卡住周期至 CONFIRMED 前。

**Eng review（/plan-eng-review，本轮只做 Track A，追加锁定）：**
- **D1 强制改密过滤器读标记**：`MustChangePasswordFilter` 每请求按 username 重查 `sys_user.must_change_password`（不用登录时 principal 缓存），DB 读异常 fail-closed（403）+ 记日志。
- **D2 改密强度规则**：新密码 ≥8 位 + 至少一个字母一个数字 + 不等于旧密码 + 不等于默认 `123456`。
- **D3 只强制新激活账号**：`must_change_password` 仅激活时置 true，V26 默认 false，不回溯已有账号。
- **D4 改密后注销会话**：`change-password` 成功后 `invalidate` 当前 session + 清标记，前端提示「密码已更新，请重新登录」跳 `/login`（闭合被盗会话窗口）。
- **V26 拆分**：V26 只含 Track A（`DEFAULT_INITIAL_PASSWORD` seed + `must_change_password` 列）；`PRESIDENT` 项目角色 / `PRESIDENT_RETURN_TIMES` 归 Track B（与 V27 一起做）。

## Success Criteria

- 总裁用自己工号登录，只能看到/确认自己负责的项目，不能越权看别人项目。
- 退回单项目，其它项目照常流转；全部确认后 ADMIN 才能发布；发布前员工查不到结果（`isResultVisible` 对 CONFIRMED 返回 false）。
- 激活账号：工号 + 123456 登录，首登强制改密；改密前除改密/登出/me 外所有接口 403。

## What I noticed about how you think

- 你纠正我「总裁不止有一个，而是有很多个总裁，不同的项目是由不同的总裁确认的」——你没有接受我把总裁当全局单角色的第一版假设，这是对真实组织结构的准确直觉，比「一个总裁盖全部章」更贴近你们公司实际。
- 「单个退回，不要影响其他人正常流转流程」——你本能地在控制爆炸半径，一个项目出问题不该拖垮整个周期，这是做多角色工作流的人才会有的敏感度。
- 「项目角色分配需要分配总裁角色……同时用户管理不是有个总裁角色吗，需也分配上，因为总裁也需要分配能够使用的功能权限」——你脑子里清楚地区分了「定位人（谁负责哪个项目）」和「功能权限（能用哪些功能）」两套角色体系，这正好命中代码里 `project_role` vs `user_role` 的分层。
