# Design: Phase 2.1 校准确认（最小闭环）

## Problem Statement

Phase 2.0 打分闭环结束后，考核停在 SUBMITTED：分打完了，但没人校准、没人确认、员工看不到结果。Phase 2.1 补完「校准确认」后半段，让 200 人的考核真正「出结果」。

## Demand Evidence

- HR 现用 Excel 手工汇总，单周期 2-3 周；Phase 2 目标是「HR 配置 + 发起」降到 <2 小时。
- 系统已投入 Phase 1 + 2.0，有明确的内部 sponsor 与资源承诺。
- 会话中确认：继峰存在独立的「总裁」终审角色，考核必须走完确认环节才算完成。

## Status Quo

打分完成后，结果靠 Excel 汇总 + 人工核对 + 逐级签字。成本 = 2-3 周 HR 时间；跨项目打分松紧不一致，没有统一校准手段。

## Target User & Narrowest Wedge

- PD（绩效负责人）：跨项目拉平分数。
- 总裁：终审确认。
- 员工：查看本人结果。
- 最小可交付：PD 在汇总矩阵改分拉平 → 总裁确认 → 锁定 → 员工看原始分明细。

## Constraints

- 数据隔离：PD 仅见标记为主 PD 的项目（**新增 inline 过滤逻辑**，不是纯复用 `@PreAuthorize`）；员工仅本人；总裁全员。
- 评估人提交后分数锁定，不可再改；PD 改分走独立审计，不退回重评。
- 结果在总裁确认后才对员工可见。

## Premises

- P1 终审链 = 打分 → PD 拉平校准 → 总裁确认 → 锁定 → 员工查看。
- P2 校准唯一目的 = 跨项目公平（拉平松紧）；🟢🔴 高亮 = 偏离该职能/项目平均分太远（阈值规则见 Open Questions）。
- P3 PD 用「改分」拉平，不退回重评。注：2.0 的 `TaskStateMachine` 已含 RETURN/RETURNED/WITHDRAW；本决策 = 不建 PD 退回 UI，RETURN 路径保持不触发（是否显式移除见下）。
- P4 结果页 = 原始分 + 明细 + 凭证，不做等级/排名（凭证渲染依赖对象存储，见 Open Questions）。

## 数据模型与状态机（2.1 增量）

- `assessment_score` 增加 `adjusted_score` 列（PD 改分后分数；原始分保留在 `score`），需要新 Flyway 迁移（V12 之外）。
- 新增 `score_adjustment` 审计表：task_id / score_id / adjusted_by / old_score / new_score / reason / created_at——谁在何时把几分改成几分、为什么。
- 任务状态：新增 `CALIBRATED`（PD 改分完成）→ 复用 `CONFIRMED`（总裁确认终态）→ `LOCKED`（结果已发布，员工可见）。2.0 的 `CONFIRMED` 语义从「PD 确认」复用为「总裁确认」，需在状态机里显式写清。
- 退回相关：2.0 已实现 RETURN/RETURNED/WITHDRAW + 「RETURN 超限自动 CONFIRMED」。D3 决定不建 PD 退回 UI；RETURN 枚举保留不触发，或作为 work item 显式移除。此移除是破坏性改动，须单独列一条工作项，不可当成免费。

## Approaches Considered

- A 最小 2.1（采用）：校准（改分 + 离群高亮 + 审计）+ 总裁确认 + 结果查询 + 跨记录比重校验。砍退回 UI、等级映射、校准建议算法；催办降级为「复用 notification 的单个按钮」。
- B 完整 2.1（否）：加回退回重评 + 等级映射 + 建议算法——把刚砍掉的复杂度加回，退回/建议算法大概率死路径，等级线需 HR 先定。
- C 分两段发布（否）：总裁确认被推迟，与「有独立总裁确认」冲突；两段间有临时锁定状态，上线节奏更乱。

## Recommended Approach

A（最小闭环一次做完）。五个决策已把方向收敛清楚，一次做完整比分两段干净；退回重评与等级映射记作 Phase 2.2 候选。

## Open Questions

- 🟢🔴 高亮阈值：默认「项目 × 职能 内偏离平均分 ±1σ」标记离群，待 PD 确认用 σ / IQR / 固定阈值，以及基准是职能平均还是项目平均。
- 改分粒度：默认改「加权总分（composite）」，原始各指标分保留；是否支持按项目批量拉平，待 PD 确认。
- 凭证对象存储：`uploadEvidence` 当前写 `/uploads/evidence/{uuid}` 占位路径、未接对象存储。结果页要渲染凭证，需先把对象存储接入（2.1 前置），或本周期先不渲染凭证。
- 改分后是否通知被改分的评估人？
- 总裁确认页形态：全员矩阵 or 汇总 + 确认按钮（业务未确认时的 fallback = 汇总 + 按钮）。
- 投入比重跨记录校验：在 2.1 范围内（2.0 遗留小项），只校验 PENDING/APPROVED（是否含 REJECTED 待定）。

## Success Criteria

- 200 人周期从「打分完成」到「结果发布」，HR/PD/总裁合计操作 <1 天（区别于 2.0 的「HR 配置 <2 小时」）。
- PD 在一个视图看到跨项目松紧差异并改分（离群高亮可用）。
- 员工在总裁确认后看到本人原始分 + 明细 + 凭证（凭证渲染以对象存储接入为前提）。
- 改分保留原始分 + 审计日志；无 PD 退回 UI。

## The Assignment

开工前，拿一张汇总矩阵线框给继峰的 PD 和总裁看，确认三件事：(1) PD 认可「拉平 = 改分不退回」；(2) 🟢🔴 离群高亮对 PD 有用、他认得出离群点（并顺带敲定阈值和改分粒度）；(3) 总裁确认页他要全员矩阵还是汇总 + 按钮。拿到这三条业务确认，2.1 需求才算真正锁死。
